# สนามประลอง: ประวัติโจมตี + ตั้งรับ (สเปก 2/2)

วันที่: 2026-08-27 · ทำต่อจาก `2026-08-27-pvp-live-board-design.md` (สเปก 1)

## ปัญหา

ตอนนี้บุกเสร็จแล้วผลหายไปเลย ไม่มีร่องรอย — ผู้เล่นไม่รู้ว่าเมื่อวานตีใครไปบ้าง และ**ไม่มีทางรู้เลยว่ามีใครมาบุกทีมเราบ้าง**
ทีมที่จัดไว้ทำหน้าที่เป็นฝ่ายรับให้คนทั้งชั้นปีบุกอยู่ทุกวัน แต่เจ้าตัวไม่เคยเห็นผลสักครั้ง — เป็นฟีเจอร์ที่มีอยู่แล้วแต่มองไม่เห็น

## กำแพงที่ต้องข้าม

`firestore.rules` ห้ามเขียน doc ของคนอื่นเด็ดขาด ⇒ **เมื่อ A บุก B, A เขียนได้แต่ของ A เท่านั้น**
จะให้ B เห็นว่า "A มาบุก" จึงเขียนตรงๆ ไม่ได้ ต้องอ้อม

## ทางออก: ฝากไว้ในแถว roster ของผู้บุก

rules ของ `roster/current` อนุญาตให้เขียนเฉพาะแถวตัวเอง:
```
allow update: if request.auth != null
  && request.resource.data.rows.diff(resource.data.rows)
       .affectedKeys().hasOnly([request.auth.uid]);
```
⇒ **ผู้บุกจดผลของตัวเองลงแถวตัวเอง · ฝ่ายรับสแกนทุกแถวหาคนที่บุกตัวเอง**

**ต้นทุน = 0** — roster ถูกโหลดอยู่แล้ว 1 read ตอนเข้าหน้า และมี write หลังทุกไฟต์อยู่แล้ว (เรตเปลี่ยน → `syncRosterRow`) แค่ payload ใหญ่ขึ้นเล็กน้อย ไม่มี read/write/collection/rules เพิ่มแม้แต่จุดเดียว

## รูปข้อมูล

เพิ่มฟิลด์ `h` ในแถว roster (ต่อจาก `tm`) — เก็บ **5 รายการล่าสุด ใหม่สุดอยู่หน้า**:
```js
h: [{ u: 'uidเป้าหมาย', w: 1, c: 250, t: 1756... }]
//   u = ใครถูกบุก · w = 1 ชนะ / 0 แพ้ · c = เหรียญที่ได้ · t = Date.now()
```
คีย์สั้นตามธรรมเนียมแถว roster (`n`, `r`, `tm`, `tb`) เพราะทุกไบต์คูณด้วยจำนวนคนทั้งชั้นปี
ขนาดที่เพิ่ม ≈ 5 รายการ × ~45 ไบต์ × 105 คน ≈ **24KB** จากลิมิต 1MB ต่อ doc — ปลอดภัย แต่ **ห้ามเพิ่มจำนวนรายการโดยไม่คำนวณใหม่**

**บันทึกเฉพาะไฟต์กับคนจริง** — บอทไม่มีแถวใน roster และไม่มีใครต้องเห็นฝั่งตั้งรับของบอท (`opp.isBot` → ข้าม)

`t` ใช้ `Date.now()` ฝั่ง client (`serverTimestamp()` ใส่ใน array ไม่ได้) ⇒ เวลาเพี้ยนได้ถ้านาฬิกาเครื่องเพี้ยน ยอมรับได้ ใช้แค่เรียงลำดับและโชว์ "เมื่อกี้/ชั่วโมงที่แล้ว"

## การอ่าน

```
ประวัติการบุกของเรา  = rows[myUid].h                    (ตรงๆ)
ประวัติการตั้งรับ    = ทุกแถว → h → กรอง u === myUid    (สแกนในหน่วยความจำ)
                       แล้วเรียงตาม t ใหม่สุดก่อน · เอา 10 รายการ
```
ชื่อผู้บุกดึงจาก `rows[attackerUid].n` ที่มีอยู่แล้ว · ผลจากมุมฝ่ายรับต้อง**กลับด้าน** (`w: 1` ของผู้บุก = เราแพ้)

สแกน 105 แถว × 5 รายการ = 525 รอบ ทำใน `computed` ได้สบาย ไม่ต้อง cache

## UI

ส่วนใหม่ท้ายหน้า `/arena` — 2 แท็บในกล่องเดียว ค่าเริ่มต้นที่ "ตั้งรับ" (ของที่ไม่เคยเห็นมาก่อน น่าดูกว่า)

```
┌ ประวัติ ─────────────────────────┐
│  [ ตั้งรับ ]  [ เราไปบุก ]        │
│  🛡️ ธีร์ บุกเรา — เรารอด  +0     │
│  🛡️ มายด์ บุกเรา — เราแพ้ 2 ชม.  │
│  … (ว่าง → "ยังไม่มีใครมาบุกเลย") │
└──────────────────────────────────┘
```
ฝั่งตั้งรับ **ไม่มีเหรียญของเรา** (เราไม่ได้อะไรจากการถูกบุก) — โชว์แค่ผลกับเวลา ไม่ต้องโชว์ `c` ของผู้บุก

## สิ่งที่จะไม่ทำ

- ไม่แจ้งเตือน / ไม่มี badge นับ (จะกลายเป็นความกดดันในแอปเรียน)
- ไม่ให้รางวัลจากการตั้งรับ (ต้องเชื่อเลขที่คนอื่นจด — ดูข้อจำกัดล่าง)
- ไม่มีปุ่ม "แก้แค้น" (ต้องข้ามกติกากระดานสุ่ม)
- ไม่เก็บ replay ของไฟต์ (ใหญ่เกินกว่าจะยัดใน roster)

## ข้อจำกัดที่ต้องรู้

- **ทุกคนเห็นประวัติของทุกคน** — `h` อยู่ใน doc ที่ทุกคนอ่านได้ ⇒ "ใครตีใคร" เป็นข้อมูลสาธารณะทั้งชั้นปี
  ในบริบทเพื่อนร่วมรุ่นถือเป็นความสนุก แต่ต้องตั้งใจให้เป็นแบบนั้น ไม่ใช่หลุดโดยบังเอิญ
- **ผู้บุกเป็นคนจดผลของตัวเอง ⇒ โกหกได้** (ซ่อนที่ตัวเองแพ้) แอปนี้ trust-based อยู่แล้วทั้งระบบ และการโกหกได้อย่างเดียวคือ "ทำให้ตัวเองดูดี" ไม่ได้เหรียญเพิ่ม ⇒ ไม่คุ้มจะกัน
  **นี่คือเหตุผลที่ห้ามผูกรางวัลใดๆ กับฝั่งตั้งรับ**
- ถ้าแอดมินกด "สร้าง roster ใหม่" ประวัติทั้งหมดหาย (`buildRosterFromUsers` สร้างแถวจาก user doc ซึ่งไม่มี `h`) — ยอมรับได้ ประวัติเป็นของชั่วคราว 5 รายการ แต่ต้องเขียนเตือนไว้ในปุ่มแอดมิน

# สเปก: หอคอย — Vertical Progress Path (ไต่บันไดขึ้นข้างบน) + เพื่อนบนเส้นทาง

วันที่ 22 ส.ค. 2026 · brainstorm กับ user เสร็จแล้ว (อนุมัติดีไซน์ 22 ส.ค.)

## ที่มา

user กำลังจะรื้อระบบเพ็ทเพื่อทำ **P3 passive** (ดู [[rxtu10_pet_overhaul]]) แต่อยากให้ UI กับอนิเมชัน
"เริ่ดก่อน โดยที่รันบนมือถือไม่แลค" — งานนี้จึงเป็น **งาน UI ล้วน** ที่เคลียร์ทางให้ P3 ลงทีหลัง

**ปัญหาที่สเปกนี้แก้:** หน้าหอคอยตอนนี้เล่าความคืบหน้า **ซ้อนกันสองระบบในการ์ดใบเดียว**
(`TowerView.vue` บล็อก `.tw-climb`)

1. แถบ progress แนวนอน 100 ชั้น (`.tw-track*`) — เห็นภาพรวมแต่ไม่มีรายละเอียด
2. แถวชิป 6 ก้อนเรียงแนวนอน (`.tw-chip*`) — เห็นรายละเอียดแต่มองไม่เห็นว่าหอสูงแค่ไหน

ทั้งคู่บอกเรื่องเดียวกัน กินที่สองแถว และไม่มีอันไหนให้ความรู้สึก "ไต่ขึ้น" ซึ่งเป็นแก่นของฟีเจอร์
ชิปยังเป็น `<div>` ที่โฟกัสด้วยคีย์บอร์ดไม่ได้ และแตะไม่ได้เลย

user ขอเพิ่มระหว่าง brainstorm: **อยากเห็นเพื่อนอยู่บนหอคอยด้วย เป็นไอคอนวงกลม**

## ขอบเขต

**ทำ**

1. แทนที่ `.tw-climb` ทั้งบล็อกด้วยเส้นทางแนวตั้งซิกแซก **100 ชั้น เลื่อนได้** ในกล่องสูง ~45% จอ
2. ปักหมุดเพื่อนทั้งรุ่นลงบนชั้นที่ตัวเองพิชิตได้ (`towerBest`) เป็นวงกลม avatar ซ้อนกัน
3. แตะโหนดชั้นไหนก็ได้ → แผงรายละเอียดชั้นนั้น (ทีมบอท / โบนัส / เพื่อนที่ชั้นนี้)
4. อนิเมชันไต่ขึ้นหนึ่งขั้นหลังชนะ + อนิเมชันปลดล็อกหมุดโบนัส
5. แตกไฟล์: `TowerView.vue` (304 บรรทัด) → view + 2 คอมโพเนนต์ + 1 ไฟล์ตรรกะล้วนที่เทสได้

**ไม่ทำ — จงใจ**

- ไม่แตะกลไกเกมแม้แต่นิดเดียว: `towerFloors.js` (สูตรบอท/เกรด/ธาตุ/โบนัส), `useTower.js` (fight/patch/roster sync),
  `battleEngine.js`, `firestore.rules`, `userSchema.js` — **ตัวเลขทุกตัวเท่าเดิม**
- ไม่เพิ่มการอ่าน Firestore แม้แต่ครั้งเดียว (`loadRoster()` ถูกเรียกอยู่แล้วใน `onMounted`)
- ไม่ให้เลือกชั้นที่จะสู้ — ยังสู้ได้แค่ชั้นปัจจุบันเหมือนเดิม แผงชั้นอื่นเป็น read-only
- ไม่มีอนิเมชันตอนแพ้ ไม่มี pulse บนชั้นปัจจุบัน ไม่มี scroll-reveal (user เลือกเฉพาะ 2 จังหวะในข้อ 4)
- ไม่แตะการ์ดสู้ (ศัตรู/ทีมคุณ/ปุ่มจัดทีม/ปุ่มสู้), `BattleReplay`, `TeamPicker`, `PetDetailModal`
- ไม่แตะ `docs/`, ROADMAP, หรือหน้าอื่น

**เลื่อนไปรอบหลัง**

- P3 passive (คนละโปรเจกต์ — สเปกนี้จงใจไม่แตะโครงข้อมูลเพ็ทเลยเพื่อไม่ให้ชนกัน)
- ทีมบอทชั้น 70+ ที่จะถูกรื้อตอน P3 (ดู [[rxtu10_tower_rebalance]])

## `utils/towerCrowd.js` — ตรรกะล้วน

```js
/**
 * roster rows → เพื่อนที่ปักหมุดรายชั้น (สำหรับเส้นทางหอคอย)
 * @param {Object} rows   `roster/current`.rows = { [uid]: row }  (row.n ชื่อ · row.p googlePhoto · row.tb towerBest)
 * @param {string} meUid  uid ตัวเอง — ตัดออกจากราง (ตัวเองมี marker แยกอยู่แล้ว)
 * @returns {Map<number, {shown: Friend[], extra: number, all: Friend[]}>}
 */
export function buildFloorCrowd(rows, meUid)
```

- `Friend = { uid, name, photo }`
- นับเฉพาะแถวที่ `tb >= 1` (ยังไม่เคยชนะ = ไม่ปักหมุด)
- ตัด `uid === meUid` ออก
- **อ่านจาก `rosterRows` ดิบ ไม่ใช่ `rosterUsers`** — `rosterUsers` key ด้วย `studentId`
  ทำให้ตกเพื่อนที่เป็น guest ทั้งหมด (`roster.js:rosterToMembers` แยก guest ไปอีกอาเรย์)
- เรียงในแต่ละชั้นด้วยชื่อ (`localeCompare`) เพื่อให้ลำดับ**คงที่ข้าม render** ไม่กระพริบสลับที่
- `shown` = 3 คนแรก · `extra` = จำนวนที่เหลือ · `all` = ครบทุกคน (ใช้ใน `FloorSheet`)

**เทส** `node --test src/utils/towerCrowd.test.js`:
กองกันเกิน 3 คน → `shown.length === 3` และ `extra` ถูกต้อง · ตัวเองไม่โผล่ในราง ·
guest (`row.g` ไม่ null) ติดมาด้วย · `tb = 0` ไม่ปัก · `rows` ว่าง/undefined → Map ว่าง ·
ลำดับคงที่เมื่อสลับลำดับ key ขาเข้า

### ผลพลอยได้: แก้การ์ดเทียบเพื่อนให้นับตรงกัน

`TowerView.vue` computed `rivals` ปัจจุบันอ่าน `membersStore.rosterUsers` → ตกเพื่อน guest
เมื่อ path อ่านจาก `rosterRows` แล้ว หน้าเดียวกันจะนับเพื่อนได้ไม่เท่ากันสองที่ จึงเปลี่ยน `rivals`
ให้อ่านจาก `rosterRows` ด้วย (`towerRanking()` เดิมไม่ต้องแก้ แค่เปลี่ยนแหล่งที่ป้อนเข้าไป)

**เรียงชั้น 100 บนสุด → ชั้น 1 ล่างสุด** · เปิดหน้ามา scroll ให้ชั้นปัจจุบันอยู่กลางกล่อง

### ตัวเลขที่ใช้จริง

| ของ | ค่า |
|---|---|
| ความสูงแถว `ROW_H` | 60px (คงที่ทุกแถว — สำคัญกับข้อ perf 3 และ 6) |
| ปุ่มโหนด | 108 × 44px (touch target ผ่านเกณฑ์ 44px) |
| วงเพื่อน | 26px ซ้อนกัน −9px |
| marker | 30px |
| ฟอนต์เลขชั้น | `.78rem` |
| ป้าย `+N` | `.72rem` |

ฟอนต์ทุกจุด ≥ `.7rem` ตามกฎ CLAUDE.md

### สถานะโหนด — ต่างกันที่สีพื้น + ไอคอน ขนาดคงที่เสมอ (ไม่มี layout shift)

| สถานะ | เงื่อนไข | หน้าตา |
|---|---|---|
| ผ่านแล้ว | `n <= best` | พื้น**สีโซนจาง** จาก `floorZone(n).color` + ✅ + ขอบ ink ปกติ |
| ปัจจุบัน | `n === floor` | พื้น `--gold` + ⚔️ + ขอบ 3px + `--pop` เด่นขึ้น + `aria-current="step"` |
| ล็อก | `n > floor` | พื้น `#f1f5f9` + 🔒 + `opacity: .6` |
| หมุดโบนัส | `n ∈ TOWER_BONUS_FLOORS` | ทับสถานะข้างบน: ขอบ dashed ทอง + 🪙 มุมขวาบน |

**พื้นโหนดที่ผ่านแล้วใช้สีโซน** — เลื่อนย้อนดูทางที่ผ่านมาจะเห็นสีไล่ 5 โซน
(🟢 ลานประลอง → 🔵 หอเวทเก่า → 🟣 ปราการอสูร → 🟡 ยอดหอคอยมังกร → 🟪 บัลลังก์ราชันย์)
ได้ความรู้สึกระยะทางฟรีโดยไม่ต้องมีข้อความอธิบาย

### เส้นเชื่อมทแยง

วาดด้วย `linear-gradient(to bottom right, …)` (และ `to bottom left` สำหรับแถวสลับ)
บน `::before` ของแถว โดยตั้ง `left`/`right` ให้กินช่วงจากกึ่งกลางโหนดหนึ่งไปอีกโหนด

เลือกวิธีนี้เพราะ**ยืดตามความกว้างจอทุกขนาดโดยไม่ต้องคำนวณมุมด้วย JS**
(ทางเลือกอื่น: SVG ต่อแถว = +200 element · `rotate()` คำนวณด้วย JS = ต้องผูก resize listener)
เส้นช่วงที่ผ่านแล้วใช้สีโซน ช่วงที่ยังไม่ถึงเป็นเทาประ · เส้นเชื่อมเป็น pseudo-element จึงไม่นับเป็น DOM node

### รางเพื่อน

อยู่**ฝั่งตรงข้ามโหนดเสมอ** → ไม่มีทางทับกัน
รางทั้งราง (รวมป้าย `+N`) เป็นปุ่มเดียว `emit('pick', n)` **ตัวเดียวกับที่โหนดส่ง** — เปิดแผงเดียวกัน
`<img>` ใช้ `row.p` (googlePhoto) ถ้ามี พร้อม `loading="lazy"` + `decoding="async"`
และ `@error` สลับไป `letterAvatar(name)` จาก `utils/avatar.js` (data-URI SVG ไม่ยิงเน็ต ไม่มีรูปแตก)

บนจอมีเพื่อนโผล่พร้อมกันไม่เกิน ~3 คน × 6 แถว = 18 รูป · นอกจอไม่ถูกโหลดเลยเพราะ lazy

### ปุ่ม "↓ ไปชั้นฉัน"

โผล่บนหัวเฉพาะตอนเลื่อนออกห่างจากชั้นปัจจุบัน — กันหลงตอนไถดูชั้น 90 แล้วกลับไม่ถูก
ตรวจด้วย `IntersectionObserver` **ตัวเดียว**จับโหนดปัจจุบัน (ไม่ผูก scroll event — ดูข้อ perf 4)

### marker ของผู้เล่น

วางแบบ `position: absolute` ในกล่องเนื้อหา (ไม่ใช่ลูกของโหนด) แล้วกำหนดตำแหน่งด้วย
`transform: translate3d(x, y, 0)` ที่คำนวณตรงจาก `floor` — แถวสูงเท่ากันทุกแถว
`y = (TOWER_MAX − floor) × ROW_H` จึงเป็นสูตรตรงๆ ไม่ต้องวัด DOM

เลือกแบบนี้เพราะถ้า marker เป็นลูกของโหนด การย้ายข้ามโหนดจะต้องทำ FLIP (วัดตำแหน่งก่อน-หลังแล้วชดเชย)
ซึ่งอ่านค่า layout กลางอนิเมชัน = บังคับ reflow · แบบ absolute เปลี่ยนแค่ `transform` ตัวเดียว

### Accessibility

โหนดเป็น `<button>` จริง มี `aria-label` เต็มประโยค เช่น
`"ชั้น 39 กำลังท้าทาย เพื่อน 9 คนอยู่ชั้นนี้"` · กล่องเป็น `role="list"`
ต่างจากชิป `<div>` ชุดเดิมที่โฟกัสด้วยคีย์บอร์ดไม่ได้และแตะไม่ได้

## อนิเมชัน

### ปัญหาลำดับเวลาที่ต้องแก้ก่อน

`fight()` ใน `useTower.js` เรียก `patchUser` แบบ optimistic → `floor` ในสโตร์ขยับ**ตั้งแต่ BattleReplay ยังเปิดอยู่**
ถ้าปล่อยตามนั้น พอปิด replay มา marker จะอยู่ที่ใหม่แล้ว ไม่มีอะไรให้ดู

**แก้:** `TowerView` ถือ `displayFloor` / `displayBest` ที่**หน่วงไว้ระหว่าง replay เปิด** แล้วปล่อยตอนปิด
`TowerPath` แค่ `watch` prop ที่เพิ่มขึ้นแล้วเล่นซีเควนซ์ — **ไม่ต้อง `defineExpose` เมธอด**
คอมโพเนนต์ยังคุยกันผ่าน props ทางเดียว

- ตอน mount ตั้ง `displayFloor = floor` เฉยๆ (watcher ไม่ใช่ `immediate`) → รีโหลดหน้าไม่มีอนิเมชันหลอน
- แพ้ → `floor` ไม่เปลี่ยน → watcher ไม่ทำงาน → ไม่มีอนิเมชัน (ตรงตามขอบเขต)

### ซีเควนซ์ไต่ขึ้น (~1.2 วิ)

| # | เวลา | เกิดอะไร | คุณสมบัติที่อนิเมต |
|---|---|---|---|
| 1 | 0 ms | เลื่อนให้ชั้นเป้าหมายมากลางกล่อง | `scrollTo({behavior:'smooth'})` |
| 2 | 260 ms | โหนดที่เพิ่งผ่านพลิก ⚔️ → ✅ เด้งเล็กน้อย | `transform: scale()` |
| 3 | 300 ms | เส้นเชื่อมช่วงนั้นไล่สีจากล่างขึ้นบน | `clip-path: inset(100% 0 0 0) → inset(0)` |
| 4 | 340 ms | marker กระโดดขึ้นหนึ่งขั้นเป็นเส้นโค้ง | `transform` ชั้นนอก (ย้าย) + ชั้นใน (โก่ง −12px) |
| 5 | 860 ms | ถ้าข้ามหมุด 20/40/60/70: วงแหวนระเบิด + ป้าย "+20,000/วัน" ลอยขึ้นจาง | `transform` + `opacity` |

- ขั้น 3 (`clip-path`) เป็นจุด**เดียว**ที่เกิด paint จริง และเป็นกล่อง ~130×60px ทีละอันเดียว —
  ต่างจากที่เคยเจอใน BattleReplay ที่ raster การ์ดเต็มใบทุกหมัด (ดู [[rxtu10_battle_perf]])
- marker: ชั้นนอกใช้ `transition: transform .5s cubic-bezier(.34,1.3,.64,1)` (ย้ายตำแหน่ง)
  ชั้นในใช้ `@keyframes` โก่งขึ้น −12px ที่ 50% → ได้เส้นโค้งโดยไม่ต้องคำนวณ path
- ขั้น 5 วงแหวนเป็น element ที่สร้างตอนเล่นแล้ว**ลบทิ้ง** ไม่ค้างใน DOM
- **แตะตรงไหนระหว่างไต่ = ข้ามไปสถานะปลายทางทันที**

### `prefers-reduced-motion: reduce`

ข้ามทั้งหมด — ตั้งค่าปลายทางทันที, `scrollTo({behavior:'auto'})`, ไม่มีวงแหวน
**ผลลัพธ์สุดท้ายต้องเหมือนกันเป๊ะ** (แพทเทิร์นเดียวกับ `utils/farmfx.js`)

## งบประสิทธิภาพบนมือถือ

กฎที่ยึดตลอดทั้งงาน — ถอดมาจากบทเรียน BattleReplay โดยตรง:

1. **อนิเมตเฉพาะ `transform` / `opacity`** — ห้าม animate `box-shadow`, `filter`, `background`,
   `width`/`height`/`top`/`left` เด็ดขาด (ข้อยกเว้นเดียวคือ `clip-path` ขั้นที่ 3)
2. **ไม่มี `filter: drop-shadow` บนอะไรที่ขยับ** — นี่คือตัวการ paint-bound ตัวจริงในเคสเก่า
3. **`content-visibility: auto` + `contain-intrinsic-size: auto 60px` บนทุกแถว**
   → เบราว์เซอร์ข้าม layout+paint ของ ~94 แถวนอกจอ
   แถวสูงเท่ากันเป๊ะทุกแถว ค่า intrinsic จึงตรงจริง = **ไม่มี scrollbar กระตุก**
4. **ไม่มี scroll event listener แม้แต่ตัวเดียว** — scroll เป็น native ล้วน
   (สำคัญมากกับ momentum scroll บน iOS) · ปุ่ม "ไปชั้นฉัน" ใช้ `IntersectionObserver` ตัวเดียว
5. **`will-change: transform` เฉพาะ marker และเฉพาะช่วงกำลังไต่** — ใส่ค้าง = จอง compositor layer กินแรมตลอด
6. **ตำแหน่ง scroll ตอนเปิดหน้าคำนวณตรงๆ** `scrollTop = (TOWER_MAX − floor) × ROW_H − boxH/2 + ROW_H/2`
   ไม่พึ่ง `scrollIntoView` → ตั้งได้ก่อนเฟรมแรก ไม่มีอาการวาบจากชั้น 100 แล้วค่อยไถลง
7. **รูปเพื่อน `loading="lazy"` + `decoding="async"` + ขนาดตายตัว 26px** — นอกจอไม่ยิงเน็ต ไม่มี layout shift

**จำนวน element ทั้งกล่อง:** 100 ปุ่มโหนด + วงเพื่อนเฉพาะชั้นที่มีคนจริง ~120 + marker 1 ≈ **~250**
(เส้นเชื่อมเป็น pseudo-element ไม่นับ) — น้อยกว่า `FarmGrid` ตอนปลดแปลงเต็มด้วยซ้ำ

### ทำไมไม่ virtualize

100 แถวเล็กเกินกว่าจะคุ้มกับความเสี่ยง — virtualize ต้องผูก scroll listener ซึ่งบน iOS momentum scroll
เสี่ยงเรนเดอร์ไม่ทันเป็นช่องว่างขาว และโค้ดซับซ้อนกว่ามาก `content-visibility: auto`
ให้ผลเดียวกัน (ข้าม layout+paint นอกจอ) โดยเบราว์เซอร์จัดการเอง scroll ยังเป็น native ล้วน
จุดคุ้มทุนของ virtualization จริงๆ อยู่ที่ 1,000+ แถว

- `node --test src/utils/towerCrowd.test.js` — ตรรกะ crowd (เคสตามหัวข้อ `towerCrowd.js` ข้างบน)

- `grep -rnE "font-size:\s*\.[0-6][0-9]?rem" src/` — ต้องไม่เจออะไร (กฎฟอนต์ `.7rem`)
- ทดลองใน `npm run dev`:
  - เปิดหน้าหอคอย → ชั้นปัจจุบันอยู่กลางกล่องตั้งแต่เฟรมแรก ไม่วาบจากชั้น 100
  - เลื่อนขึ้น-ลงยาวๆ ด้วยนิ้ว → ไม่มีช่องว่างขาว ไม่กระตุก
  - แตะโหนดชั้นสูงๆ → แผงเปิด แสดงบอทถูกต้อง และ **`#bottom-nav` ไม่ทับก้นแผง**
  - ชนะหนึ่งชั้น → ปิด replay แล้วเห็น marker ไต่ขึ้น (ไม่ใช่กระโดดไปแล้วตั้งแต่แรก)
  - ชนะชั้น 20 → เห็นวงแหวนหมุดโบนัส
  - เปิด reduce-motion ใน OS → ทุกอย่างยังทำงาน แค่ไม่มีอนิเมชัน และค่าปลายทางตรงกัน
- ต้องให้ user เทสบนมือถือจริงก่อนปิดงาน (เครื่อง user เป็นเกณฑ์สุดท้ายของคำว่า "ไม่แลค")

## ความเสี่ยงที่รู้ตัว

- **`content-visibility: auto` + `IntersectionObserver`** — โหนดที่ถูกข้ามการเรนเดอร์ยังต้องรายงาน
  intersection ได้ถูกต้อง ถ้าเบราว์เซอร์ไหนเพี้ยน ปุ่ม "ไปชั้นฉัน" อาจไม่โผล่/ไม่หาย
  → เป็น progressive enhancement ล้วน ปุ่มไม่ทำงานก็ยังเลื่อนเองได้ ไม่บล็อกการเล่น
- **เส้นทแยงจาก gradient** อาจมีขอบหยักเล็กน้อยบนบางความกว้างจอ — รับได้เพราะเป็นเส้นตกแต่ง
  ถ้าออกมาแย่จริงค่อยเปลี่ยนเป็น SVG ต่อแถวพร้อม `vector-effect="non-scaling-stroke"`
- **เพื่อนกองที่ชั้น 70 เยอะมาก** (จุดตันโบนัส) — รางแสดง 3 + "+N" อยู่แล้ว
  แต่ `FloorSheet` ต้องเลื่อนได้ ถ้ามีคนเป็นสิบ (`BottomSheet` มี `.sheet-scroll` ให้แล้ว)

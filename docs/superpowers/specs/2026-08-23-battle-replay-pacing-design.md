## 1. ปัญหา & วินิจฉัย

ผู้เล่นกดปุ่ม "ข้ามไปผล" เป็นนิสัย · user สั่งให้ **เอาปุ่มข้ามออก** และทำให้ replay สนุกพอที่จะไม่มีใครอยากข้าม

**วัดจริง** (รัน `simulateBattle` 200 seed, ทีม 4v4 เกรดกลาง):

| ตัวเลข | ค่า |
|---|---|
| จำนวนหมัดต่อไฟต์ | เฉลี่ย **26.9** (ต่ำสุด 21 สูงสุด 34) |
| เวลาต่อหมัด | windup 250ms + พุ่ง/ยิง 280–500ms + `baseDelay` 380ms ≈ **~1.0s** |
| เวลาไฟต์รวม | **~27 วินาที** |

**วินิจฉัย:** ปัญหาไม่ใช่คุณภาพอนิเมชัน (v3 Scene/FX split แก้เรื่องกระตุกจบแล้ว user บอก "ลื่นมาก") แต่คือ **ทุกหมัดถูกเล่าด้วยน้ำหนักเท่ากันหมด**

engine ส่งข้อมูลที่บอกความสำคัญของแต่ละหมัดมาครบแล้ว — `crit`, `eff`, `dmg`, `targetHpAfter`, `dead` — แต่ `BattleReplay.vue` แปลงทุกหมัดเป็น "เงื้อ → พุ่ง → เลขเด้ง" ชุดเดียวกัน ต่างแค่ตัวเลข ผลคือ**จังหวะราบเรียบ 27 รอบติดกัน ไม่มีจุดพีค ไม่มีจุดพัก** สมองผู้เล่นอ่านจบภายใน 3 หมัดแรกว่า "อีก 24 หมัดที่เหลือจะเหมือนกันเป๊ะ" แล้วมองหาปุ่มข้าม

**ขอบเขตที่ user ตัดสินแล้ว:**
- **ผลไฟต์ยังคำนวณล่วงหน้า 100%** ไม่แตะ engine ไม่มี input จากผู้เล่นที่เปลี่ยนผล (แนวทาง A จาก 3 ทางเลือก)
- **ไม่ทำโหมดเร่งอัตโนมัติตอนไต่รัว** — ผมเสนอไป user ปฏิเสธด้วยเหตุผลว่าแต่ละแมตช์มีความลุ้นในตัว + P3 passive กำลังจะมาเพิ่มความหลากหลาย → **ทุกไฟต์ได้การเล่าแบบเดียวกันหมด ไม่มีเงื่อนไขตามจำนวนครั้ง** (ตัดสินใจแล้ว ไม่ต้องรื้อ)

## 2. หลักการออกแบบ (doctrine ของงานนี้)

1. **หมัดที่สำคัญกว่า ต้องกินเวลานานกว่า ตัวใหญ่กว่า และดังกว่า** — เวลาไม่ใช่ค่าคงที่ต่อหมัดอีกต่อไป แต่เป็นงบที่จัดสรรตามน้ำหนักของเหตุการณ์
2. **ความหนักของหมัดหนัก มาจากความเบาของหมัดเบา** — กับดักคือ "ใส่ juice ให้ทุกหมัด" ซึ่งได้ 27 หมัดดังเท่ากัน = ไม่มีอะไรพิเศษ **ชั้น 1 ต้องจงใจให้ไม่มีอะไร**
3. **ตื่นเต้นด้วยฟิสิกส์การ์ตูน ไม่ใช่ความรุนแรง** — บีบ-ยืด, เด้งสปริงเกินขนาด, สติกเกอร์ขอบดำหนา, ดาวคอมิก, คำไทยสั้นๆ ("คริ!" "น็อก!" "รอด!") ดังด้วย**จังหวะกับขนาด** เข้ากับภาษาภาพการ์ดขอบหนาของแอปที่มีอยู่
4. **ปูก่อนตี = ความลุ้น** — เรารู้ผลล่วงหน้าอยู่แล้ว จึงเอาความรู้นั้นมา**สร้างความคาดหวัง** ไม่ใช่ปิดบัง หมัดหนักถอยเงื้อนาน 350ms มีวงแหวนเรือง คนดูรู้ตัวก่อนว่า "อันนี้มาแรงแน่" นี่ไม่ใช่การสปอยล์ แต่คือวิธีที่อนิเมะ/เกมต่อสู้สร้างความฮึกเหิม
5. **ความลุ้นตัวจริงอยู่ที่หลอดเลือด ไม่ใช่ที่หมัด** — พอการ์ดที่เลือดต่ำเต้นเป็นจังหวะหัวใจ ทุกหมัดที่ลงตัวนั้นกลายเป็นคำถาม "ตายมั้ย" โดยไม่ต้องเพิ่มอนิเมชันหมัดเลยแม้แต่นิดเดียว
6. **สืบทอดข้อบังคับ performance จาก v3 ทั้งหมด** (§6) — งานนี้ห้ามทำให้ iOS Safari กลับไปกระตุก เด็ดขาด

## 3. `src/utils/battleBeats.js` — ใหม่ (pure, ไม่มี Vue ไม่มี DOM)

หน้าที่เดียว: **แปลง log ของ engine เป็นลำดับ "beat" ที่บอกว่าแต่ละเหตุการณ์ควรถูกเล่าหนักแค่ไหน** เป็นฟังก์ชันบริสุทธิ์ ไม่อ่าน store/DOM/`Date.now` → เทสได้ด้วย `node:test` เหมือน `battleSummary.test.js`

```js
buildBeats(log, maxHpByUid) → beat[]
```

### 3.1 รูปร่าง beat

```js
{
  ...event,                 // ฟิลด์เดิมจาก engine ครบ (t, side, attacker, target, dmg, crit, eff, targetHpAfter, dead)
  tier: 'chip' | 'solid' | 'heavy' | 'finish' | null,
  dmgPct,                   // dmg / maxHp[target] — 0..1
  hpPctAfter,               // targetHpAfter / maxHp[target] — 0..1
  timing: { windup, motion, hitstop, tail },   // ms ที่ ×1
  danger,                   // true = หลังหมัดนี้เป้าเหลือ ≤25% (ยังไม่ตาย) → เปิดวงแหวนเต้น
  survive,                  // true = หมัดนี้ทำให้เป้าตกลงต่ำกว่า 10% ครั้งแรก (ยังไม่ตาย) → ป้าย "รอด!"
}
```

### 3.2 กฎแบ่งชั้น — ตรวจตามลำดับ หยุดที่ข้อแรกที่เข้าเงื่อนไข

| ลำดับ | ชั้น | เงื่อนไข |
|---|---|---|
| 1 | **finish** | `event.dead === true` **หรือ** เป็น event `t:'attack'` ตัวสุดท้ายของ log |
| 2 | **heavy** | `crit === true` **หรือ** `eff === 'super'` **หรือ** `dmgPct > 0.20` |
| 3 | **chip** | `dmgPct < 0.10` |
| 4 | **solid** | นอกเหนือจากนั้น |

- `t:'round'` → `tier: null`, `timing` ทุกช่องเป็น 0 (marker ไม่กินเวลา — พฤติกรรมเดิม)
- `t:'end'` → `tier: null`
- **event type ที่ไม่รู้จัก → `tier: null` ผ่านไปเงียบๆ ไม่ throw** (ช่องเว้นให้ P3 passive — §8)
- `eff === 'weak'` ไม่บังคับชั้น — ปกติดาเมจน้อยอยู่แล้วเลยตกไปชั้น chip เอง แต่ยังได้ป้าย callout สีเทาเหมือนเดิม

### 3.3 ตารางเวลา (ms ที่ ×1)

| ชั้น | windup | motion | hitstop | tail | **รวม** | สัดส่วนที่พบ |
|---|---|---|---|---|---|---|
| **chip** ถาก | 0 | 110 | 0 | 240 | **350** | ~50% |
| **solid** ปกติ | 140 | 130 | 40 | 290 | **600** | ~30% |
| **heavy** หนัก | 350 | 100 | 120 | 730 | **1300** | ~15% |
| **finish** ชี้ขาด | 430 | 250 | 250 | 1070 | **2000** | ~5% |

- `windup` = ช่วงเงื้อ/ปูก่อนออกตัว
- `motion` = ช่วงพุ่ง/ยิงจนถึงจังหวะกระทบ
- `hitstop` = หยุดนิ่งหลังกระทบ **ไม่มีอะไรขยับเลย** (ทำด้วย delay เฉยๆ ไม่มี visual — ตามบทเรียน v3 ที่ตัด scale ทั้งกล่องทิ้ง)
- `tail` = ดีดกลับ + ช่องว่างก่อนหมัดถัดไป

**งบเวลารวม** (27 หมัดเฉลี่ย): `13.5×350 + 8×600 + 4×1300 + 1.5×2000` ≈ **17.7s** + intro 1.1s + ค้างสนามท้ายไฟต์ 0.9s ≈ **~19.7 วินาที** (จาก ~27) โดยไม่ได้ตัดหมัดไหนทิ้งแม้แต่หมัดเดียว

ไฟต์ยาวสุดที่เจอในการวัด (34 หมัด) ≈ **25 วินาที** — ยังสั้นกว่าไฟต์*เฉลี่ย*ของระบบเดิม เกณฑ์เทสใน §10 แยกค่าเฉลี่ยกับค่าสูงสุดตามนี้

`REPLAY_CFG.baseDelay` เดิม (380ms คงที่) **ถูกยกเลิก** — เวลาทั้งหมดมาจาก `beat.timing`

## 4. สเปกการเคลื่อนไหวรายชั้น

> ⚠️ **จุดที่ปรับจากม็อกอัพที่ user อนุมัติ** — ม็อกอัพให้เป้า "บีบตัว" ทุกชั้น และให้การ์ดผู้ตีพุ่งทุกชั้น สเปกจริงตัดออกในชั้นล่างเพราะข้อบังคับ performance จาก v3 (เหตุผลเต็มใน §6) **ผลลัพธ์ที่ตาเห็นแทบไม่ต่าง แต่ราคาต่างกันมาก** และบังเอิญว่ามันไปทางเดียวกับ doctrine ข้อ 2 พอดี (ชั้นล่างต้องเบา)

### ชั้น 1 · ถาก (350ms)

**การ์ดไม่ขยับเลยทั้งสองฝั่ง** — ทุกอย่างเกิดบน FX layer ที่ promote ถาวรอยู่แล้ว

- melee: สไปรต์ jab เล็กพุ่งจากผู้ตีไปเป้าแล้วจาง (`fx.jab`) · ranged: projectile เดิม (ซึ่งอยู่บน FX layer อยู่แล้ว)
- ขอบการ์ดเป้าแวบแดง 250ms (`classList` — พฤติกรรมเดิม ไม่ใช่ animation)
- เลข 0.9rem จางขึ้น 14px ใน 420ms ไม่มีสปริง
- **ไม่มี** เงื้อ · **ไม่มี** จอสั่น · **ไม่มี** hitstop · **ไม่มี** ดาวคอมิก

### ชั้น 2 · ปกติ (600ms)

- ผู้ตี: **`el.animate()` ตัวเดียว keyframes ครบวงจร** `none → ย่อถอย translateY(14px) scale(1.06,.9) → พุ่ง translateY(-100px) scale(.9,1.18) → none` ด้วย `fill:'none'` (ข้อบังคับ v3 — ห้ามแตกเป็นหลาย animation)
- เป้า: **ไม่ขยับ** — สื่อการกระทบด้วยขอบแวบแดง + ดาวคอมิกเล็ก 34px บน FX layer
- เลข 1.15rem เด้งสปริงเกินขนาด (scale .3 → 1.35 → 1) ลอยขึ้น 22px
- หลอดผีขาวไล่ตามหลัง 450ms (§5)
- **ไม่มีจอสั่น** (ข้อบังคับ §6.2 — จอสั่นสงวนไว้ให้ชั้น 3–4 เท่านั้น) น้ำหนักของชั้นนี้มาจาก hitstop 40ms + ดาวคอมิก + การ์ดพุ่งจริง ซึ่งเพียงพอแล้ว

### ชั้น 3 · หนัก (1300ms)

- **เงื้อ 350ms พร้อมวงแหวนเรืองทอง** (`fx.ring` ที่มีอยู่แล้ว ยืดเวลาจาก 250 เป็น 350) — นี่คือหัวใจของความลุ้นทั้งงาน
- ผู้ตี: animation ตัวเดียวเหมือนชั้น 2 แต่ถอยลึกกว่า (24px) พุ่งเร็วกว่า (100ms) ยืดตัวมากกว่า (`scale(.82,1.3)`)
- **เป้าบีบตัว** (`el.animate()` ตัวเดียว squash-and-spring 420ms) — ชั้นนี้ขึ้นไปเท่านั้น
- ดาวคอมิก 66px + เลข 1.7rem สีทอง + ป้าย "คริ!" (แดง) หรือ "แพ้ทาง!" (ส้ม)
- จอสั่น 5px 2 รอบ + hitstop 120ms
- `tail` ยาว 730ms โดยตั้งใจ — **ให้อากาศหายใจหลังหมัดหนัก** ไม่ใช่รีบต่อ

### ชั้น 4 · ชี้ขาด (2000ms)

- เงื้อ 430ms วงแหวนเรืองเข้มสุด
- พุ่ง **250ms** (ช้ากว่าชั้น 3 ที่ 100ms โดยตั้งใจ = ฟีลสโลว์โมชัน)
- hitstop **250ms** — จอนิ่งสนิท นี่คือเฟรมที่ผู้เล่นจะจำได้
- ดาวคอมิก 92px · จอสั่น 8px 3 รอบ + เอียง 0.6° · เลข 2.3rem + ป้าย "น็อก!"
- เป้า: หมุนกระเด็นออก `translate(70px,-60px) rotate(150deg) scale(.6)` + จาง 520ms + 💨 puff แล้วติดคลาส `dead` (เทา) — แทน `koPuff` เดิม
- ถ้าเป็นหมัดสุดท้ายที่ไม่ได้ฆ่าใคร (ชนะด้วย %HP) → ใช้ทุกอย่างยกเว้นท่อนหมุนกระเด็น

## 5. หลอดเลือด = ตัวสร้างความลุ้นตัวจริง

ตอนนี้หลอดหดปุ๊บทันที (`transition: transform .2s`) ไม่มีใครทันรู้สึกอะไร เพิ่ม 3 อย่าง:

1. **หลอดผี** — `<i class="br-hp-ghost">` สีขาว opacity .75 อยู่**หลัง** `.br-hp-fill` หดตามหลัง 450ms หน่วง 160ms ทำให้ *เห็น* ว่าเพิ่งเสียไปเท่าไหร่ (เทคนิคเดียวกับเกมต่อสู้)
2. **โซนอันตราย** — `beat.danger` (เลือดเหลือ ≤25% ยังไม่ตาย) → เปิดวงแหวนแดงเต้นเป็นจังหวะหัวใจทับการ์ดนั้น **ผ่าน FX pool** (`fx.dangerRing(uid, on)`) ไม่ใช่คลาสบนการ์ด — เหตุผลใน §6.3 · ปิดเมื่อตายหรือจบไฟต์
3. **รอดหวุดหวิด** — `beat.survive` → ป้าย "รอด!" เขียวเด้ง · เงื่อนไขคือ**ตกจาก ≥10% ลงต่ำกว่า 10% เป็นครั้งแรกของตัวนั้น** (ไม่ใช่ "อยู่ต่ำกว่า 10%") เพื่อไม่ให้ป้ายเด้งซ้ำทุกหมัดที่ตามมา

## 6. ข้อบังคับ performance (สืบทอดจาก v3 — ข้อนี้สำคัญที่สุดในสเปก)

v3 แก้อาการกระตุกบน iOS Safari ด้วยการวินิจฉัยว่าต้นเหตุคือ **raster churn ของการ์ดเต็มใบ** งานนี้เพิ่มการเคลื่อนไหวเข้าไปอีก จึงต้องนับต้นทุนทุกบรรทัด

### 6.1 งบ promotion ต่อวินาที — ต้องไม่แย่ลงกว่าเดิม

"promotion window" = 1 ครั้งที่การ์ดจริงถูก animate (raster ตอน promote + reintegrate ตอน demote ≈ 2 raster event)

| | ของเดิม | ของใหม่ |
|---|---|---|
| ต่อหมัด | 1 (ทุกหมัด melee) | chip **0** · solid **1** · heavy **2** · finish **2** |
| ต่อไฟต์ | ~27 | `13.5×0 + 8×1 + 4×2 + 1.5×2` = **19** |
| ต่อวินาที | 27/27 = **1.00** | 19/19.7 = **0.96** |

**ผลลัพธ์: เท่าเดิมหรือดีกว่านิดหน่อย** ทั้งที่ดูมีชีวิตชีวาขึ้นมาก เพราะครึ่งนึงของหมัดทั้งหมด (chip) ไม่แตะการ์ดเลย

⚠️ **นี่คือเหตุผลที่ chip ห้ามมี card lunge** — ถ้าใส่ chip เป็น 350ms พร้อม lunge จะกลายเป็น ~2.9 promotion/วินาที = เกือบ 3 เท่าของ v3 ที่พิสูจน์แล้วว่าพอดีเพดาน จะวนกลับไปกระตุกแน่นอน

### 6.2 จอสั่น = ของเสี่ยงที่สุดในสเปกนี้ ต้องวัดก่อนเชื่อ

v3 **ตัด hitstop แบบ scale ทั้ง `.br-box` ทิ้ง** ด้วยเหตุผลตรงๆ ว่า *"re-raster เต็มจอ @DPR3 ทุก crit (แพงสุด คุ้มน้อยสุด)"* — จอสั่นคือของตระกูลเดียวกันเป๊ะ

ข้อบังคับ:
- จอสั่น**เฉพาะชั้น 3 กับ 4 เท่านั้น** (~20% ของหมัด — ชั้น 1–2 ห้ามสั่นเด็ดขาด)
- ทำด้วย **`el.animate()` ตัวเดียวบน `.br-box`, `transform` อย่างเดียว, `fill:'none'`**
- **ตัดสินด้วยพาเนลทดสอบ (§11) บน iPhone จริง ไม่ใช่ด้วยการเดา** — จอสั่นเปิดเฉพาะ preset `high` เท่านั้น ถ้า `high` แดง (>33ms ซ้ำๆ ตรงจังหวะชั้น 3–4) ก็เลือก `mid` ซึ่งไม่มีจอสั่น จบ ไม่ต้องแก้โค้ด
- **ถ้าสุดท้ายเลือก `mid`/`low`** ให้ชดเชยความหนักของชั้น 3–4 ด้วย **ดาวคอมิกใหญ่ขึ้น + hitstop ยาวขึ้น 40ms** (ทั้งคู่ราคาถูก — ดาวอยู่บน FX layer, hitstop คือการไม่ทำอะไรเลย) ความรู้สึกหนักจะยังอยู่ครบ

### 6.3 ห้าม animation วนไม่รู้จบบนการ์ด

โซนอันตราย (§5.2) เป็นการเต้นต่อเนื่อง = ถ้าทำบนการ์ดจะเป็น **layer ค้างถาวร** ซึ่งคือ fix#3 ที่ v3 พิสูจน์แล้วว่าพัง → บังคับให้ทำผ่าน **FX pool element ที่ promote ถาวรอยู่แล้ว** ทับบนการ์ด (`fx.dangerRing`) และ animate แค่ `opacity`

### 6.4 ข้อบังคับที่ยกมาทั้งดุ้นจาก v3

- lunge = `el.animate()` **ตัวเดียว** keyframes ครบวงจร `fill:'none'` — ห้ามแตกขาไป/ขากลับ
- keyframes มีแต่ `transform` — `zIndex` ตั้ง static ก่อนเริ่ม/เคลียร์หลังจบ ห้ามอยู่ใน keyframes
- ห้ามแตะ paint property ของการ์ด (border/class) ระหว่าง animation รัน — เปลี่ยนให้เสร็จก่อนสั่ง animate
- ของอายุ < 1 วิ ห้ามอยู่ใน Vue reactivity — ทุกอย่างใน §4 ที่เป็น ephemeral ต้องอยู่ใน FX pool
- ทุก motion ใหม่เป็นของ `battleFx` ไม่ใช่ของ component — เพื่อให้โดน `cancelAll()` เก็บกวาดจาก registry เดียว

## 7. ปุ่มควบคุม — เอา "ข้ามไปผล" กับ "เร็ว ×N" ออก

### 7.1 ทำไมปุ่ม "เร็ว" ต้องออกไปด้วย

`เร็ว ×4` บีบ 350/600/1300/2000ms ให้เหลือ 87/150/325/500ms — **ทุกชั้นยุบเป็นเนื้อเดียวกัน หมัดหนักไม่หนักอีกต่อไป** เท่ากับออกแบบจังหวะทั้งหมดแล้วแจกปุ่มปิดมันให้ผู้เล่นเอง มันคือปุ่มข้ามที่ปลอมตัวมา

**แถบล่างเหลือปุ่ม "พัก" ปุ่มเดียว** (ยังจำเป็น เพราะแตะดูตัวเพ็ท = พักอัตโนมัติ)

### 7.2 กดค้าง = เร่ง (ไม่ใช่ออก)

**ข้อเท็จจริงที่ต้องยอมรับก่อน:** `TowerView.vue:195-196` เรียก `fight()` ซึ่ง `patchUser` ขยับชั้น**เสร็จเรียบร้อยแล้วก่อน** replay จะเปิด แปลว่า replay เป็นการนำเสนอล้วนๆ **รางวัลจ่ายไปแล้ว** → ทางออกอะไรก็ตามที่ใส่เข้าไปย่อมทำหน้าที่เป็นปุ่มข้ามได้เสมอ ห้ามไม่ได้ เลือกได้แค่ว่าจะทำให้มันสะดวกแค่ไหน และจะให้มันพาไปไหน

**กลไก:**
- กดค้างที่พื้นที่สนาม → วงแหวนวิ่งรอบนิ้ว **400ms** → เข้าโหมดเร่ง
- **ระหว่างค้าง**: `timing` ของ **ชั้น 1 กับ 2 คูณ 0.3** (chip 350→105ms, solid 600→180ms)
- **ปล่อยนิ้ว** → กลับความเร็วปกติทันที (เป็น fast-forward แบบกดค้าง ไม่ใช่สวิตช์)
- **ค้างจนจบ log** → เข้าหน้าสรุปตามปกติ (ไม่ใช่ปิดจอทิ้ง — ผู้เล่นยังได้ดู MVP/สรุปดาเมจ)
- แตะสั้นๆ 1 ครั้งโดยไม่ค้าง → ขึ้นคำใบ้จางๆ "กดค้างเพื่อเร่ง" 1.5 วิ (ค้นพบได้ตอนที่ต้องการ แต่ไม่ล่อตาตอนที่ไม่ต้องการ)

**กติกาที่ทำให้มันไม่ใช่ปุ่มข้าม:**

> **โหมดเร่งไม่แตะชั้น 3 และชั้น 4 — หมัดหนักและหมัดชี้ขาดเล่นเต็มความยาวเสมอ ต่อให้กดค้างอยู่**

ผลคือ "เร่ง" ไม่ใช่การข้ามไฟต์ แต่เป็น **ปุ่มเรียกไฮไลต์** คนรีบก็ยังได้ดูคริครบ ได้ดูหมัดน็อกแบบสโลว์โมชันครบ แล้วจบที่หน้าสรุป

**ตัวเลขจริงของโหมดเร่ง** (แก้จากที่ประเมินไว้ตอนคุยว่า 6–7 วิ ซึ่งมองข้ามงบของชั้น 3–4 ไป): กดค้างตั้งแต่วินาทีแรกจนจบ = `13.5×105 + 8×180 + 4×1300 + 1.5×2000` ≈ **11.1 วินาที** (จาก 19.7) — ลดลง ~44% โดยชั้น 3–4 กินไป 8.2 วิซึ่งแตะไม่ได้ตามกติกา ในทางปฏิบัติผู้เล่นมักกดค้างกลางทางไม่ใช่ตั้งแต่ต้น จึงได้น้อยกว่านี้ ถือว่ายอมรับได้ และช่วง chip/solid ที่วิ๊ดผ่านไปเร็วคือสิ่งที่อ่านออกว่า "กำลังเร่งอยู่"

### 7.3 ของเดิมที่คงไว้ไม่แตะ

- intro **READY? → GO!** (~1.1s) แตะข้ามได้เหมือนเดิม
- แตะการ์ด = พัก + เปิด inspect popover
- หน้าสรุปผล + peek สนาม + ปุ่มปิด — ไม่แตะ
- `Teleport to body` (ข้อบังคับ CLAUDE.md ข้อ 6 เรื่อง stacking context) — ไม่แตะ
- Escape ปิด modal สรุป — ไม่แตะ

### 7.4 ตอนจบไฟต์

หมัดสุดท้ายเป็นชั้น 4 เสมอ (กฎ §3.2 ข้อ 1) → เล่นจบแล้ว **ค้างสนามไว้ 900ms** (จากเดิม `resultDelayMs: 500`) ให้หมัดน็อกได้ลงจอดก่อนเปิด modal สรุป

## 11. พาเนลทดสอบใน Admin (user เสนอ — แทนที่การเดาแล้วค่อยแก้)

§6.2 เดิมเขียนว่า "ทำไปก่อน วัดแล้วถ้าแดงค่อยถอย" ซึ่งแปลว่าต้อง build จนเสร็จก่อนถึงจะรู้ว่าเดาถูกไหม พาเนลนี้เปลี่ยนเป็น **ลองจริงบนเครื่องจริงแล้วค่อยตัดสิน** → `battleFx` ต้องรับ preset เป็นพารามิเตอร์**ตั้งแต่ออกแบบ** ไม่ใช่มาแปะทีหลัง

### 11.1 สองแกนที่ปรับแยกกัน

**แกน A — ความอลังการของภาพ** (ตอบคำถาม "แลคมั้ย")

| | `high` สวยสุด | `mid` กลาง | `low` เบา |
|---|---|---|---|
| การ์ดผู้ตีพุ่ง (§4 ชั้น 2+) | ✓ | ✓ | **✗ ไม่มีเลย** |
| เป้าบีบตัว (ชั้น 3+) | ✓ | ✗ | ✗ |
| จอสั่น (ชั้น 3–4) | ✓ | ✗ | ✗ |
| ดาวคอมิก · เลข · วงแหวนเงื้อ · หลอดผี · hitstop · วงแหวนอันตราย | ✓ | ✓ | ✓ |

`low` = โหมด lite ที่ v3 พิสูจน์แล้วว่าลื่น 60fps บน iPhone **บวกการเล่าเรื่อง 4 ชั้นเต็มรูปแบบ** (จังหวะ/เลข/ดาว/หลอดผี อยู่บน FX layer ซึ่งแทบไม่มีราคา) → **พื้นปลอดภัยรู้อยู่แล้ว** การทดสอบนี้ถามว่า "เอาไปได้ถึงไหน" ไม่ใช่ "จะรอดมั้ย"

**แกน B — จังหวะ** (ตอบคำถาม "สนุกมั้ย") — คูณ `beat.timing` ทั้งชุด

| | `grand` อลังการ | `normal` กลาง | `tight` กระชับ |
|---|---|---|---|
| ตัวคูณ | ×1.25 (~24s) | ×1.0 (~19.7s) | ×0.8 (~16s) |

> **แกน A ไม่แตะจังหวะเลย · แกน B ไม่แตะต้นทุน GPU เลย** — สองแกนอิสระต่อกันสนิท ไม่ว่าเลือก preset ไหน การเล่าเรื่อง 4 ชั้นยังอยู่ครบ

### 11.2 `src/utils/battleReplayPrefs.js` — ใหม่ (pure + localStorage)

```js
FX_PRESETS   // { high: {cardLunge, targetSquash, screenShake}, mid: {...}, low: {...} }
PACE_PRESETS // { grand: 1.25, normal: 1.0, tight: 0.8 }
readPrefs()  // → { fx, pace } · อ่าน localStorage · ค่าผิด/ไม่มี → ค่าเริ่มต้นที่ hardcode ไว้
writePrefs({ fx, pace })
```

- **เก็บลง localStorage ของเครื่องนั้นเครื่องเดียว ไม่แตะ `config/app`** — นักศึกษาที่กำลังเล่นอยู่ต้องไม่โดนผลกระทบระหว่าง user ทดสอบบนมือถือตัวเอง
- `battleBeats.buildBeats()` **ไม่รู้จัก pace** — คืน `timing` ที่ ×1 เสมอ (คงความเป็นฟังก์ชันบริสุทธิ์) ตัวคูณไปใช้ตอน consume ใน component

### 11.3 พาเนลใน `AdminView.vue`

- ปุ่มเลือกแกน A (3 ปุ่ม) + แกน B (3 ปุ่ม) — เห็นค่าปัจจุบันชัด
- **ปุ่ม "ยิงไฟต์ทดสอบ"** — เปิด `BattleReplay` ตรงจากพาเนลด้วย **seed ตายตัวที่เป็นเคสหนักสุด: 4v4 melee ล้วน ไฟต์ยาว คริเยอะ** · ไม่ต้องไต่หอคอย ไม่เสียทรัพยากรใดๆ ไม่เขียน Firestore ยิงซ้ำได้ไม่จำกัด · **เป็นไฟต์เดียวกันเป๊ะทุกครั้ง** จึงเทียบ preset กันได้จริง
- เปิด fps meter อัตโนมัติในไฟต์ทดสอบ (ไม่ต้องพิมพ์ `?fps=1` บนมือถือ)
- **สรุปตัวเลขหลังไฟต์**: เฟรมแย่สุด (ms) · จำนวนเฟรมที่เกิน 33ms · จำนวนเฟรมที่เกิน 16ms → ตัดสินด้วยตัวเลข ไม่ใช่ความรู้สึก

### 11.4 หลังทดสอบเสร็จ

เอา preset ที่ user เลือก **ฮาร์ดโค้ดเป็นค่าเริ่มต้น** ใน `battleReplayPrefs.js` แล้ว**เก็บพาเนลไว้เป็นเครื่องมือถาวร** (จะได้ใช้ซ้ำตอน P3 passive เพิ่ม FX ใหม่) — ดีกว่าเพิ่มฟิลด์ใน `config/app` ที่ผู้ใช้ทุกคนต้องอ่านตลอดไปเพื่อค่าที่เปลี่ยนปีละครั้ง

- ❌ เสียง — ยังไม่มีระบบเสียงในแอป ไม่เปิดประเด็นในงานนี้
- ❌ กล้อง zoom/pan — ราคาแพงบน WebKit (re-raster ทั้งฉาก) ผิด doctrine v3 ตรงๆ
- ❌ แตะ `battleEngine.js` — งานนี้ไม่มีเหตุผลต้องเปลี่ยนตัวเลขสมดุลใดๆ
